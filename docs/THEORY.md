# Краткая теория и защита RowColDemo

Конспект к `Row and Column.pdf`, с. 1–13, с разбором фактической реализации. Соответствие конкретных коммитов и рисунков — REQUIREMENTS.md. Это учебное объяснение, не отчёт нового запуска.

## Оси и вложенность

**Row** размещает детей по горизонтали, **Column** — по вертикали. Вложенность позволяет получить сетку: в этапе 05 верхний Row содержит столбцы 1/2/3, 4/5/6, 7/8, затем отдельный нижний Row содержит 9/10/11. Отсутствующий третий элемент справа — действительно пустая область, не невидимая ячейка.

**Alignment** задаёт положение по поперечной оси: verticalAlignment у Row, horizontalAlignment у Column. **Arrangement** работает по основной оси: horizontalArrangement у Row, verticalArrangement у Column. Чтобы Center/End/Bottom были заметны, в контейнере должно остаться свободное пространство. Start/End — логическое начало/конец; рисунки лекции предполагают направление LTR, а не универсальное физическое «слева/справа».

## Интервалы

- SpaceEvenly: одинаковое свободное расстояние между детьми и по краям.
- SpaceBetween: свободное пространство распределяется между детьми, по краям дополнительного нет.
- SpaceAround: свободное расстояние по краям вдвое меньше внутренних интервалов.

Сравнивать нужно внешние слоты детей. У TextCell есть собственный padding 4 dp: даже при SpaceBetween рамка не обязана касаться края родителя. На узком экране свободного пространства мало, поэтому варианты могут выглядеть близко.

## Modifier, scope и базовые линии

RowScope/ColumnScope дают контекст для align/weight: данные ребёнка интерпретирует соответствующий родитель. Индивидуальный align задаёт положение конкретного ребёнка по поперечной оси. ColumnScope.alignBy относится к вертикальным линиям выравнивания и горизонтальному положению; это не выравнивание текста по горизонтальной baseline, как в Row.

FirstBaseline — базовая линия первой строки текста, LastBaseline — последней. Разные размеры шрифта дают разные положения базовой линии внутри прямоугольника Text. Поэтому одинаковый верхний край не означает одинаковое основание букв. В Row `alignByBaseline()` — удобная запись для `alignBy(FirstBaseline)`; в учебных примерах участвующие тексты оба предоставляют линии для выравнивания.

В этапе 26 большой текст выравнивается по LastBaseline, малый — по своей первой линии; в 27 большой меняется на FirstBaseline. **Исходный PDF сохраняет 32.sp у малого текста; отсутствие этого размера в архивных этапах 26–28 — ошибка реализации, а не правило Compose.**

`paddingFrom(FirstBaseline, before = 80.dp, after = 0.dp)` задаёт минимальные расстояния относительно линии с учётом ограничений измерения, а не обычный padding сверху 80 dp. В примере 28 у Small Text нет alignByBaseline: paddingFrom сам по себе не связывает базовые линии соседей. Нулевой after не убирает естественную часть текста ниже baseline. PaddingFrom не следует понимать как модификатор, доступный исключительно в RowScope, несмотря на группировку в лекции.

## Вес и размеры

Вес — положительное относительное значение, не обязательно процент и не обязательно в диапазоне до единицы. Row распределяет оставшуюся ширину, Column — оставшуюся высоту. Дети без веса занимают предпочитаемый размер в допустимых constraints, после чего оставшееся пространство распределяется между весовыми детьми. `fill = true` заполняет выделенный слот.

В этом проекте все три ребёнка весовые: 0.2/0.4/0.3 задают отношение 2:4:3; сумма не обязана равняться 1. Проверка `actualMeasuredWidthsFollowTwoFourThreeWeights` сравнивает измеренные размеры с этим отношением и добавляет собственные горизонтальные поля ячейки к ширине Text. Именно выделенный слот второй ячейки должен быть вдвое шире первого; видимые рамки после вычета одинаковых полей не имеют строго такого же отношения.

`size(100.dp)` — предпочтительный размер, ограниченный constraints. В финальном весовом Row ширину задаёт выделенный слот; объявление size не возвращает каждой ячейке безусловные 100 dp. `width(1000.dp)` также не превращает телефон в экран 1000 dp. Wide Preview и телефон проверяются отдельно.

**dp** применяется для геометрии с учётом плотности; **sp** — для текста с учётом масштаба шрифта. Поэтому фиксированная ячейка не гарантирует, что глифы 80 sp или двузначные числа не обрежутся при любых настройках.

## Осмысленные поправки к лекции

1. Используется RowColDemoTheme вместо скопированного имени StringsDemoTheme.
2. Входной modifier применяется один раз. В PDF `cellModifier` уже начинается с modifier, поэтому последующий `.then(modifier)` повторил бы эффекты входной цепочки. В проекте Text получает только cellModifier.
3. Scaffold innerPadding передаётся корневому контейнеру MainScreen один раз; в baseline/weight-примерах проекта он не теряется.
4. Утверждение PDF «все ColumnScope-модификаторы работают по горизонтальной оси» неточно: weight в Column распределяет высоту.
5. Утверждение о процентном весе 0…1 не является ограничением API; здесь важны относительные коэффициенты.
6. Удаление `fontSize = 32.sp` на этапах 26–28 НЕ относится к этим исправлениям. Это несоответствие D1 из REQUIREMENTS.md.

## Семь вопросов для защиты

1. **Чем различаются Alignment и Arrangement?** Первая настройка действует поперёк потока детей, вторая — вдоль него.
2. **Почему Center иногда ничего не меняет?** Контейнер обтекает содержимое и не имеет свободного места для сдвига.
3. **Чем отличаются Evenly, Between и Around?** У Evenly все свободные интервалы равны; у Between нет крайних; у Around крайние вдвое меньше внутренних.
4. **Зачем RowScope/ColumnScope?** Они предоставляют модификаторы, смысл которых задаёт конкретный родитель, например align и weight.
5. **Зачем выравнивать baseline, а не прямоугольники Text?** Разные шрифты/размеры имеют разное положение основания букв; baseline выравнивает текст типографически.
6. **Что означают веса 0.2/0.4/0.3?** Отношение 2:4:3 выделенного пространства; это не неполные 90 процентов экрана. В Column аналогичный механизм управляет высотой.
7. **Почему нельзя повторять входной modifier и терять innerPadding?** Повторение удваивает эффекты цепочки, а потеря системных отступов может разместить контент под системными панелями. Поэтому нужны отдельные измерительные тесты и реальная UI-проверка.
